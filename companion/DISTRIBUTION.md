# Companion distribution contract

Single version authority: `version.json`. Build both distributions together with `python3 stage_release.py`. The outputs are staging-only, not production. The legacy standalone bookmarklet remains the recovery tool; do not rename it as a synchronized Stable release. No Stable pair yet. Existing candidate uses shared merchant fields and timing, but separate queue/UI implementations: this work synchronizes build and distribution, not full source parity.

## Release procedure

1. Change shared source/version and run existing synthetic regression suite, package checks, channel tests. Commit source changes on the authorized feature branch. Keep raw card credentials out of all source and logs.
2. `python3 stage_release.py --source-revision "$(git rev-parse HEAD)"` from `companion/`. The command verifies the clean source commit and emits `staging/companion/dev/{bookmarklet.js,extension.zip,release.json}` plus `staging/companion/launcher.txt`. The digest covers version, source and release scripts; the Git commit identifies the exact checked-in revision. Never publish a local descriptor with null sourceRevision.
3. Copy the staged Dev pair and launcher into the PWA's `public/companion/` only under release authorization, keeping Stable unchanged. Review and deploy via existing PWA process. Both distributions show the shared version; the bookmarklet shows the selected channel. The extension ZIP is byte-identical on promotion, so its installed header identifies the version, not a mutable channel. The download location and release descriptor identify the channel.
4. Test normal hosted script loading with a noncredential, inert fixture before enabling a hosted merchant build. If merchant CSP blocks loading, do not bypass it: keep the standalone generated bookmarklet. Never fetch executable remote code in the extension. Do not switch a live helper silently or auto-start checks.
5. After integrated acceptance and explicit approval, `python3 promote_release.py --accepted-version VERSION --accepted-source-revision FULL_SHA --authorize-stable`. This validates source identity, versions and hashes and copies the exact Dev bytes to staging Stable. Deploy the staged Stable pair only with separate production authorization. No rebuilding during promotion. Keep previous approved release recoverable in Git history.

Paths after authorized deployment: `/companion/launcher.txt`, `/companion/dev/{bookmarklet.js,extension.zip,release.json}`, `/companion/stable/{bookmarklet.js,extension.zip,release.json}`. Until Stable is populated, its launcher option reports unavailability. The launcher defaults to Dev via primary action and focus; selecting a channel only loads the helper. No credentials are included in requests to the PWA. Existing Batch v1 and merchant request behavior unchanged. This staging architecture does not establish permission for merchant automation.
